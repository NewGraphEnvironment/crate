## Findings

- **[severity: fragile]** data-raw/forms_derive-schemas.R:278-292 — the QML ValueMap arm (`cols_from_qml`) keeps QGIS's NULL sentinel, though the CSV arm drops `<NULL>` (line 191) and the header says the placeholder is dropped (line 56). QGIS stores an allow-NULL value map's empty entry as `<Option name="&lt;NULL&gt;" value="{2839923C-8B7D-419E-B84B-CA2FE9B80EC7}"/>`, and the xpath `.//Option[@name='map']//Option[@name and @value]` matches it. Reproduced on a 3-choice snippet: values come back `"{2839923C-...}", "1", "5"`, so `values_numeric()` is FALSE and `out$type <- "string"` retypes an integer-coded column (a 1–5 score, say) as string. That column then gets a sentinel GUID as an allowed value. rfp@a901caa's `form_monitoring.qml` has no such entry today (its only `NULL` text is in a COALESCE display expression), so the committed YAMLs are correct. The header names re-running at a newer RFP_SHA as how form changes reach crate, so the next re-run against a QML with an allow-NULL value map writes the wrong type. Fix: drop options whose `name` is `<NULL>` (or whose value is the sentinel) in the QML arm, the same as the CSV arm.
  - **Rule:** code-check.md "A fix lands in one of two callers that share a harness"

- **[severity: fragile]** data-raw/forms_derive-schemas.R:383 and :392, generated as `upstream_variants[].cols` in all five `form_*.yaml` — elsewhere `cols` holds a variant's **full** column set. `crt_ingest()` matches with `setequal(variant$cols, raw_cols)` (R/crt_ingest.R:92), and `track_sessions.yaml`, a `schema_only` entry, lists all of its plugin layer's columns. In the form schemas the build variant's `cols` is `[fid, geom]` (the columns the reader drops), and the 2025 monitoring variant's `cols` is `[rowid, utm_zone, easting, northing]` (the columns it has that the build lacks). So one key means three different things, two of them inside `form_monitoring.yaml`. Nothing reads it at runtime today, because these entries are `schema_only` and `crt_ingest()` aborts on them. But the YAMLs are a published contract. A reader applying crate's own matching rule takes the pscis build to be a 2-column shape and can match no real capture against it. The full column set already exists in the fixture CSVs, so either write it into `cols`, or put these lists under keys that say what they are (e.g. `reader_drops`, `adds`).
  - **Rule:** none

- **[severity: fragile]** inst/extdata/schemas/README.md:41 and :34 — the documented grade example `{name: harvestable, requires: [record_id, x, y]}` parses with `y` as logical `TRUE` (measured: `yaml.load` gives `list("record_id", "x", TRUE)`). A grade written by copying it requires a column named `"TRUE"` and is FALSE for every row. The README's own YAML 1.1 section (line 57) warns about exactly this. The new `null` key in the table at line 34 has the same problem: written bare, as the table shows it, `null: ...` reads back as an empty-named element (yaml warns "Empty character vector used as a list name"), so `crt_schema_cols()` reports `null = NA` for that column. The generator quotes both (`'y'`, `'null'`), and the integrity test "every grade requires only columns the schema declares" catches the grade case for registered schemas. Nothing checks for a lost `null` key. Quote both in the README (`[record_id, x, "y"]`, `"null"`). Optionally, have the integrity test refuse a column spec carrying an empty-named key.
  - **Rule:** code-check.md "Bare `y`, `n`, `on`, `off`, `yes`, `no` are booleans in YAML 1.1"

- **[severity: fragile]** data-raw/forms_derive-schemas.R:117-120 (→ `form_monitoring.yaml` `rowid`, `utm_zone`) — these two extra columns are hand-typed `integer`, but the measured 2025 capture declares both `REAL` (`form_monitoring__capture-utm-columns-2025.csv:22,24`). Every other column in the file takes its type from the declaration through `decl_map` (REAL → double). `crt_schema_apply()` coerces with `suppressWarnings(as.integer(x))`, which truncates any non-integer value silently (`as.integer(10.7)` is 10). The same `rowid` and `utm_zone` columns are typed `double` in `form_pscis` and `form_fiss_site`. A real UTM zone or row id is unlikely to be fractional, so the practical risk is small. It is still the one place in the generated schemas where the canonical type contradicts the file's declaration without the gate-5 reason (non-numeric choices). Type them `double` like their pscis twins, or say in the notes why they are narrowed.
  - **Rule:** none
