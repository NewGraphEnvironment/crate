## Findings

- **[severity: fragile]** data-raw/forms_derive-schemas.R:289 (round-1 fix): the QML arm drops QGIS's NULL choice by its **label**, `name != "<NULL>"`. What makes the entry a placeholder is its **value**, the fixed sentinel `{2839923C-8B7D-419E-B84B-CA2FE9B80EC7}` that round 1 identified. The label is just the default text QGIS puts in the ValueMap table's description cell, and that cell is editable. form_monitoring is the one form whose meaning comes from a QML authored in QGIS rather than from rfp's CSV, so a crew lead could relabel the NULL row there ("Not assessed", say). If that happens, the next re-derive keeps the GUID as an allowed value, `values_numeric()` goes FALSE, and an integer-coded column is retyped `string`. That is the defect round 1 reported, reached through a different label. Today's QML has no ValueMap NULL entry, so the committed YAML is correct. The CSV arm's bare-`<NULL>` match is right for the CSV, because rfp's CSV writer emits the bare token. Fix: in the QML arm, filter on `xml_attr(o, "value") != "{2839923C-8B7D-419E-B84B-CA2FE9B80EC7}"`, or on both label and value.
  - **Rule:** code-check.md "A proxy is not the property"

- **[severity: fragile]** R/crt_schema_fingerprint.R:76 and :78: `enc2utf8()` on a UTF-8 name whose encoding is unmarked (`"unknown"`), run in a C locale, rewrites the bytes as `<c3><a9>` escapes. So the same column set gets a different fingerprint than it does in a UTF-8 session. Measured with `rawToChar(as.raw(c(0x64,0xc3,0xa9,0x62,0x69,0x74)))` ("débit", unmarked): `1-dae53876043f69f5` under en_US.UTF-8 and `1-aa9633b74f361115` under `LC_ALL=C`. The same name marked UTF-8 gives `1-dae5…` in both locales. The roxygen says "UTF-8 is the one every other producer will use", and the encoding test covers only a *marked* latin1 name, so this case is untested. How reachable it is, measured: RSQLite returns non-ASCII names marked UTF-8, so `PRAGMA table_info` input is unaffected. `sf::st_read()` under C mangles the name itself (`d.U.00E9.bit`) before crate sees it. Names that arrive from `read.csv()`/`readLines()` without `encoding = "UTF-8"` are affected. Every current form column name is ASCII, so no fingerprint in this branch moves. The cost comes later: a non-ASCII column plus a containerised harvest with no locale would make one vintage look like two, and `crt_schema_variant()` would return NA alongside a `crate_unknown_fingerprint` warning. Fix, as the rule prescribes: re-mark valid UTF-8 before converting, `Encoding(cols)[validUTF8(cols) & Encoding(cols) == "unknown"] <- "UTF-8"`, then `enc2utf8()`.
  - **Rule:** code-check-r.md "`file(open = "wb", encoding = )` does not re-encode on write"
